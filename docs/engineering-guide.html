When to Commit

✓ Smallest independently reversible unit of work
✓ "This works but is messy" — commit it, clean up in the next commit
✓ Before you start a risky change — so you have a rollback point
✗ "Added tire model AND rewrote renderer AND fixed audio" — that's 3 commits
✗ Broken code committed to main — main should always run

Architecture

Design the structure before you write the code. Every module has one job.

Warning Signs — You Need to Split

⚠
File exceeds ~300 lines

It's doing too many things. Find the natural seam and split.

⚠
Function exceeds ~40 lines

Extract named helpers. Each helper should be describable in its name alone.

⚠
Comment says "and also..."

Two responsibilities. One of them belongs somewhere else.

⚠
You scroll to find where a variable is set

State is too implicit. Move it closer to where it's used or document it explicitly.

⚠
Changing A requires changing B and C

Modules are too coupled. Introduce a clean interface between them.

Plan First — 5 Questions Before Writing Code

1. What is this module's one job?
2. What does it need to read?
3. What does it need to write?
4. What calls it, and what does it call?
5. If you can't answer those clearly — you need to read/research more before writing.

Unit Tests for VerletDrift Functions

// vitest — tests for your actual physics functions
import { describe, test, expect } from 'vitest';
import { pacejkaLateral } from '../js/physics/tires.js';

describe('Pacejka lateral force curve', () => {
  test('peaks near 8° slip angle', () => {
    const at8deg  = pacejkaLateral(0.14);   // ~8° in radians
    const at2deg  = pacejkaLateral(0.035);  // low slip — building grip
    const at30deg = pacejkaLateral(0.52);   // over-saturated — grip falls off
    expect(at8deg).toBeGreaterThan(at2deg);
    expect(at8deg).toBeGreaterThan(at30deg);
  });

  test('is symmetric — left/right produce same force magnitude', () => {
    expect(pacejkaLateral(0.1)).toBeCloseTo(-pacejkaLateral(-0.1), 3);
  });

  test('returns zero at zero slip', () => {
    expect(pacejkaLateral(0)).toBeCloseTo(0, 5);
  });
});

describe('Physics sleep', () => {
  test('car at rest with no input stays at rest', () => {
    const state = makeTestState({ vx: 0, vy: 0, throttle: 0 });
    for (let i = 0; i < 100; i++) runPhysicsStep(state, 0.01);
    expect(state.body.velocityX).toBeCloseTo(0, 3);
    expect(state.body.velocityY).toBeCloseTo(0, 3);
  });
});

What to Test First in a Physics Sim

1. Pure math functions — Pacejka curves, torque curves, weight transfer formulas (no state needed, easiest to test)
2. Edge cases — zero velocity, max throttle, boundary exactly at edge
3. Regression tests — "car should not slide when parked on flat ground"
4. Energy conservation — kinetic energy shouldn't increase without throttle input
→ Don't try to test rendering or audio — focus on pure physics functions first

TypeScript

JavaScript with types. Catches entire categories of bugs at write time — before you run anything.

💡

TypeScript compiles to plain JavaScript. Your browser never sees TypeScript — only the compiled JS. You add types gradually and it never stops being valid JS underneath.

Real Bug TypeScript Would Have Caught

In a physics sim, many values are all number but mean completely different things — meters, m/s, radians, Newtons. Without types, passing the wrong unit is invisible:

❌ JavaScript — silent bug 
// applyDrag expects speed in m/s
function applyDrag(car, speed) {
  car.forceX -= speed * speed * 0.5 * DRAG_COEFF;
}

// Called with km/h — car drags 7.7x too hard
// No error. No warning. Just wrong behavior.
applyDrag(car, state.body.speedKPH);  // bug: should be speedMPS
✅ TypeScript — caught immediately 
type Meters = number;
type MetersPerSecond = number;
type KilometersPerHour = number;
type Newtons = number;
type Radians = number;

function applyDrag(car: CarBody, speedMPS: MetersPerSecond): void {
  car.forceX -= speedMPS * speedMPS * 0.5 * DRAG_COEFF;
}

// TypeScript error at write time — before you even run it:
// Argument of type 'KilometersPerHour' is not assignable
// to parameter of type 'MetersPerSecond'
applyDrag(car, state.body.speedKPH);

Your State Object — Typed

// Type aliases for physics units (same as number, but documented)
type Meters = number;
type MetersPerSecond = number;
type RadiansPerSecond = number;
type Radians = number;
type Newtons = number;

interface CarBody {
  centerX: Meters;
  centerY: Meters;
  heading: Radians;
  velocityX: MetersPerSecond;
  velocityY: MetersPerSecond;
  angularVelocity: RadiansPerSecond;
}

interface WheelState {
  x: Meters;
  y: Meters;
  slipRatio: number;           // dimensionless, [-1, 1]
  lateralForce: Newtons;
  frictionUtilization: number; // dimensionless, [0, 1]
}

// Now if you rename `heading` to `angle`:
// TypeScript instantly shows every file that breaks.
// No more searching with Ctrl+F.

Gradual Adoption — No Big Rewrite

1. npm install -D typescript + add tsconfig.json
2. Rename one file: tires.js → tires.ts
3. Add types only to function signatures first — ignore internals
4. Fix errors one at a time — each one is a real bug or ambiguity
5. Repeat for other files at your own pace — JS and TS can coexist

State Management

A global mutable object that everything touches is a bug that's impossible to trace.

The Problem — Everyone Mutates Everything

// state is one flat object — any module can change anything
import state from './state.js';

// input.js writes this — fine
state.input.throttle = 1.0;

// physics.js writes this — fine
state.body.centerX += vx * dt;

// renderer.js writing this — wait, the renderer changes physics??
state.camera.zoom = 1.5;  // ok this is camera, but...
state.body.velocityX = 0; // ...could accidentally do this too

When camera.x is wrong, you don't know if physics set it, the renderer set it, or a UI handler set it. Debugging becomes archaeology.

Step 1 — Named Slice Exports (What We Did)

// state.js — same flat object, but named exports declare intent
const state = { /* ... all the fields ... */ };

export default state;
export const physicsState  = state;  // "physics owns this"
export const renderState   = state;  // "renderer reads this"
export const audioState    = state;  // "audio reads this"
export const uiState       = state;  // "ui controls these params"
// physics/tires.js — imports its own slice
import { physicsState as state } from '../state.js';
// Now it's obvious at a glance what this module "should" touch.
// (It's still the same object — but the name documents the intent.)

Step 2 — Encapsulation (Next Level)

Current — direct mutation 
// Any file anywhere can do this
import state from './state.js';
state.body.velocityX += impulseX;
state.body.velocityY += impulseY;
Next level — controlled interface 
// physics/body.js — only this module mutates body
let _body = { centerX: 0, centerY: 0, velocityX: 0, ... };

// Only physics can change velocity
export function applyImpulse(fx, fy, dt) {
  _body.velocityX += fx * dt;
  _body.velocityY += fy * dt;
}

// Everyone else gets a read-only copy
export function getBody() {
  return { ..._body };  // spread = copy, not reference
}

The Golden Rules

✓ Physics owns body, wheels, engine — only physics writes them
✓ Renderer reads state — it never modifies physics data
✓ Audio reads state — it writes nothing at all
✓ If you need to track something in the renderer, it gets its own renderer state — not physics state
✗ Never pass the whole state object to a function — pass only what it needs
