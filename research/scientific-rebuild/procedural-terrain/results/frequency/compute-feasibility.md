# Compute placement assessment

The measured single-vehicle workload remains a sequential 18-velocity coupled solve with roughly 16 constraint rows and several endpoint iterations. A dense representation of inverse inertia (324 doubles), Jacobian (288 doubles), free velocity and right-hand side (34 doubles) is 5,168 bytes, plus bounds/metadata; output velocity/impulse is another 272 bytes. Transfer bandwidth is not the limiting issue. At about five endpoint iterations per 1 ms step, a CPU-owned iteration would require about 5,000 dependent GPU round trips per simulated second. A 0.2 ms round trip alone would consume the entire second. Prior measured CPU unified-solve/preparation cost is about 0.16 ms per endpoint in one profiled workload. These are break-even budgets, not measured WebGPU latency.

A single workgroup could contain the small constrained solve, but cross-iteration endpoint geometry, engine/clutch modes, rollback and work checks still require a coherent owner. A CPU/GPU ping-pong design is not justified. The available renderer is verified SwiftShader with no `/dev/dri`; no hardware-GPU speedup is inferred from it. No wholesale GPU physics port or artificial large-batch benchmark is introduced. Four isolated terrain contacts do not expose useful large-batch parallelism.

Potential GPU targets are many independent vehicles, larger terrain/geometry batches, and particles. The current 3,381-vertex terrain mesh only updates on terrain/origin changes; tracks already use bounded incremental GPU buffers. No beneficial additional compute dispatch is demonstrated for the present single-vehicle application. The physical slip/work decision for rubber deposition must remain authoritative regardless of rendering placement.

A CPU Web Worker is a more credible responsiveness experiment: keep the complete solver, accumulator, atomic reset and accepted-stage observer in one worker, send ordered controls/frequency changes with accepted-step acknowledgements, and publish read-only pose/diagnostic snapshots and incremental track revisions at display frequency. For example, 20 KB at 60 snapshots/s is about 1.2 MB/s, rather than serializing the full state at every physics step. This would isolate UI latency; it does not reduce CPU seconds per simulated second or fix software rasterization. Required measurements are worker transfer/latency, determinism under timestamped input, reset/fault handling and full inherited-control/browser regressions. Such benefits are not claimed without that benchmark.

The frequency study's main fidelity limit is numerical damping from the current discrete method, not bandwidth or missing GPU parallelism. A work-consistent higher-order coupled method would need its own mathematical/vehicle validation. Reducing physical damping to compensate for coarse-step numerical loss is not justified.
