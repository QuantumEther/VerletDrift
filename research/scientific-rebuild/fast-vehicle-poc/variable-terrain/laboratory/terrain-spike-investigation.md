# RTX 5090 frame-spike investigation

Capture: user-supplied frame-diagnostics_webGPU.json, 1960 raw intervals; cinematic, yard, WebGPU, 1253×783, top camera, physics running, 100% rendering scale. Existing GPU values are asynchronously resolved render-pass batches, not total GPU/presentation time.

Using interval >6.25 ms (one and a half 240 Hz refresh intervals) and scene CPU time ≥2 ms: 316 long intervals; 284 followed a previous JS callback <4.17 ms. 21 scene spikes; 20 were followed by a long interval. Maximum scene time 9.6 ms. These results establish a strong association for the scene spikes, but they account for only 20 of 316 long intervals under these thresholds. They do not identify the other causes or prove terrain is responsible. A frame can be late because of GPU, compositor, scheduling, synchronization or earlier queued work; the capture cannot distinguish these. Physics catch-up reached 38 steps in one callback; the existing clock and fixed timestep remain unchanged.

This change adds per-frame CPU wall-time fields `terrainGeometry` (sampling, classification and position/color writes), `terrainNormals`, `terrainTexture` (CPU paint and texture-dirty marking), and `terrainUploadMark` (attribute dirty flags). They are subcomponents of `scene`, not additive to it. These fields measure CPU preparation and marking, not the actual asynchronous GPU transfer; GPU transfer/synchronization needs a browser/GPU trace. Existing per-frame `steps`, physics and frame intervals support catch-up analysis. No terrain behavior, rendering quality or physics changed and no optimization is claimed.

33 Node tests passed. For the next RTX capture use the existing frame diagnostics with the same settings and a repeatable yard route, and download raw JSON. Collect A/B measurements with terrain, smoke, lighting, scene updates, submission and physics independently controlled, using the existing paused audit for a fixed scene plus separate repeatable driving runs. Record browser GPU track/Performance trace and repeat before/after any candidate. The new fields are absent from the original capture, so attribution and measured before/after improvements remain unresolved; do not infer a 240 Hz fix from this instrumentation.
