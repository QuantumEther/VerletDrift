# WebGPU migration milestones

Branch PERFORMANCE_2. Initial isolated upgrade vendors Three.js 0.180.0 (MIT) with core, WebGL, WebGPU and TSL builds. The laboratory HTML import map maps the legacy core URL to r180 for this page only; historical pages retain r160. No physics, assets or audio changed. Existing addon loaders currently remain legacy and need explicit compatibility testing/upgrading before claiming migration completion.

Executed `node research/scientific-rebuild/fast-vehicle-poc/variable-terrain/laboratory/viewport-browser.mjs`: passed responsive viewport/control checks on Chromium at three viewport sizes under upgraded WebGL. This is not full visual parity validation. The WebGPU build is available but not selected or integrated; there is no claimed WebGPU success or measured backend comparison yet. Custom GLSL effects and direct WebGL diagnostics still require migration. Do not treat this intermediate milestone as the completed user mission.

Second milestone upgrades the local GLTF/EXR/RGBE loaders and required HDRLoader, fflate and geometry utility to the same r180 distribution. All 33 Node tests passed; responsive browser checks passed. `webgpu-capability-browser.mjs` initialized WebGPURenderer with fallback forbidden, checked `backend.isWebGPUBackend`, and rendered a TSL standard-material sphere. Result: active WebGPU, revision 180, on the cloud browser with unsafe software WebGPU flags. The screenshot and JSON are capability evidence only, not the vehicle renderer or a performance comparison. The live laboratory still uses WebGL; backend switching and custom-effect migration remain unfinished.

Backend factory milestone: `renderer-backend.js` provides explicit WebGL/WebGPU creation, asynchronous initialization, verified active backend, rendering and idempotent disposal. Capability browser tests now use this implementation. Commands `node research/scientific-rebuild/fast-vehicle-poc/variable-terrain/laboratory/webgpu-capability-browser.mjs webgl` and the same with `webgpu` both returned the requested active backend at revision 180. Records are `results/backend-*`. These remain small rendering fixtures, not laboratory integration, visual parity or benchmarks. The live laboratory is still WebGL; no UI selector or TSL effect migration is claimed.

Live initialization milestone: the laboratory's view now obtains its WebGL renderer through the asynchronous backend factory. Reset handles initialization asynchronously, ignores superseded initialization results and gates stepping while the view is absent. Existing WebGL diagnostics and effects remain active. All 33 Node tests and the three-size viewport browser check passed. This does not activate WebGPU in the laboratory: WebGL-specific diagnostics, PMREM/environment plumbing and GLSL effects still require migration before exposing that choice safely.

TSL overlay milestone: `tsl-overlays.js` implements road mark color/alpha/edge/clip behavior, radial contact shading and the eight-lobe cloud-shadow opacity in TSL node materials. `tsl-overlay-browser.mjs webgpu` successfully compiled and rendered all three in a verified WebGPU browser fixture (results/tsl-overlay-webgpu.*). These factories are not connected to the live laboratory yet. A specific smoke blocker is documented in r180 PointsNodeMaterial: WebGPU Points are one pixel; parity requires instanced camera-facing quads sharing the existing particle buffers. No smoke-disable workaround or misleading fallback was introduced. Terrain details and scattering remain unported.

Smoke billboard experiment: `tsl-smoke.js` supplies bounded instanced SpriteNodeMaterial quads sharing the existing position/opacity/diameter/tint/rotation arrays, without another particle simulation. `createWebGPUView()` exposes this opt-in view; the live WebGL laboratory remains unchanged. Initial backend-return-only tests were insufficient: a screenshot was blank despite an active WebGPU report. The new `tsl-smoke-browser.mjs` waits for GPU work and attempts render-target pixel readback. In this cloud Chromium/unsafe software WebGPU environment it failed with `A valid external Instance reference no longer exists.` This is a failed rendering validation, not a successful smoke migration. Earlier capability/overlay tests established initialization and submission only, not verified visible parity. Do not use their return status as evidence that the vehicle can be rendered in WebGPU. The instanced smoke implementation still lacks the HDR ambient sampling parity and must not replace the production effect yet.

Rendering diagnosis: a raw WebGPU fixture passes buffer readback, compute compilation, triangle rendering and queue completion without Three.js. The reduced Three.js test fails after native canvas submission in this cloud browser, but succeeds when rendering exclusively to an offscreen target. This localizes the demonstrated failure to that presentation path/configuration; it does not establish a universal Three.js or hardware failure. Offscreen pixel readback also needed a corrected 256-byte row stride: r180's last row is unpadded, so dividing total buffer length by height corrupts captures. `gpu-device-browser.mjs`, `minimal-three-browser.mjs` and `tsl-smoke-browser.mjs` preserve reproductions. The latter now produces actual visible instanced particle pixels with offscreen WebGPU and explicit readback. This is not native presentation, real-time vehicle rendering, HDR parity or performance success. The experiment retaining an explicit adapter/device did not resolve canvas submission, so that factory change was rejected.

Native presentation reproduction: `raw-native-browser.mjs` now reproduces the same queue-completion failure using a raw WebGPU canvas without Three.js. Offscreen raw rendering passes. Disabling antialiasing in the reduced Three.js test did not resolve native presentation; Vulkan, SwiftShader+Vulkan and Graphite diagnostic flags likewise failed. These results localize a cloud native-presentation/configuration limitation, not a demonstrated defect in the smoke shader. No system settings or production rendering quality were changed. The backend factory now accepts an explicit antialias diagnostic option, defaulting to the existing true.

Terrain TSL work: `tsl-terrain.js` ports surface palette weighting, world-coordinate grain, roughness and bump shading. `tsl-terrain-browser.mjs webgpu` compiled/rendered the material with pixel readback (`nonblack=120024`). It is not integrated: authored road-corridor/marking parity and exact noise fidelity are unfinished. `MeshStandardNodeMaterial.copy(legacyMaterial)` erased required node defaults in the first attempt; copying supported scalar properties explicitly corrected that implementation error. No simulator physics changes.

Live laboratory milestone: the actual scene now has explicit WebGL/WebGPU selection (reload/reset labeled), WebGPU environment prefiltering, TSL road/contact/cloud-shadow materials, authored terrain corridors/markings and instanced smoke connected to the original particle arrays. Standard vehicle materials use Three's node-renderer conversion. A separately selected offscreen target enables actual scene readback without replacing native presentation. The custom Schweinemotorwerke GLB rendered in this path with activeBackend=webgpu. No physics, assets, drivetrain or audio implementation was changed. See webgpu-laboratory.md for exact commands and unresolved items. This is experimental integration, not verified visual parity or measured real-time improvement.
